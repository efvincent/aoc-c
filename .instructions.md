# C23 Learning Project - Copilot Instructions

## Project Structure & Layout

### Directory Organization
```
src/
  main.c              # Dispatcher (you write this)
  common/
    containers.h / containers.c    # Dynamic arrays, stacks, queues, etc.
    pathfinding.h / pathfinding.c  # A*, BFS, DFS, etc.
    math_utils.h / math_utils.c    # GCD, modular arithmetic, etc.
  2024/
    day01.c / day01.h    # Parsing + part1 + part2 for 2024 day 1
    day02.c / day02.h
  2025/
    day01.c / day01.h

data/
  2024/
    day01.txt          # Input files
    day02.txt
  2025/
    day01.txt

tests/
  2024/
    day01_test.c
  2025/
    day01_test.c
```

### Execution Model
```bash
$ aoc 2024 1           # Run 2024 day 1, both parts
$ aoc 2024 1 1         # Run 2024 day 1, part 1 only
$ aoc 2024 1 2         # Run 2024 day 1, part 2 only
```

Main dispatcher parses args, loads `data/YYYY/dayDD.txt`, and calls appropriate puzzle function.

### Function Signatures
Each day exports:
```c
void day_YYYY_DD_part1(FILE *input_file);
void day_YYYY_DD_part2(FILE *input_file);
```

### File Organization Rationale
- **One `.c` + `.h` per day** — parsing and solving are tightly coupled in AoC; same file keeps logic cohesive
- **Common utilities by category** — separate headers + sources for containers, pathfinding, math, etc. (non-inline functions require `.c` files)
- **Per-year directories** — organizes growing number of puzzles and data files
- **Single executable** — `./build/aoc` dispatched by CLI args

## Source Code Lock
**You MUST NOT edit files in `src/`** unless the user explicitly grants permission in a specific request. This is a learning project.

## What You Can Edit
- Files in `tests/` — unit tests and test infrastructure
- Files in `docs/` — documentation
- Build and configuration files (Makefile, .gitignore, etc.)

## Guidance Style
When the user requests help with source code:
1. Provide clean C code fences with clear scoping comments (e.g., `// REPLACE THIS BLOCK` and `// WITH THIS`)
2. Include enough context to locate changes in the file
3. Let the user apply patches themselves — do not directly edit `src/` files
4. Include robust Doxygen documentation in all recommended code or patch guidance (file-level, type-level, and function-level comments with params, return values, ownership/lifetime notes, and error behavior where relevant)

## Algorithm Policy
**Do not suggest, describe, or hint at solutions or algorithms** for Advent of Code puzzles unless the user explicitly requests it (e.g., "explain the algorithm" or "tell me the approach").

Instead:
- Ask clarifying questions about their approach
- Point to relevant C23 language features or standard library functions
- Suggest how to structure the code or break down the problem
- Help debug their implementation

## C23 Conventions for This Project
- Use C23 features where appropriate (designated initializers, `_Bool`, generic selection, etc.)
- Self-contained executable — no external libraries beyond C23 standard library
- Build with `gcc -std=c23 -Wall -Wextra -O2`
- Keep each puzzle solution independent and easy to run/test

## Checkpoint Workflow

When you say **"checkpoint"**, execute this sequence:

1. **Code Review** — Audit the current changes in the current branch
   - Review logic, structure, memory management, error handling
   - Provide written feedback on the code (you will not edit src/)
   
2. **Documentation Audit** — Verify docs match current code
   - Update [docs/](docs/) as needed (this is editable)
   - Ensure README, references, and guides are current
   
3. **Version Bump** — Update VERSION in the main source header files
   - Use semantic versioning: MAJOR.MINOR.PATCH
   - Bump PATCH for puzzle solutions, MINOR for significant structural changes
   - Example: `#define VERSION "0.1.0"`
   
4. **Address Feedback** — If code review revealed issues:
   - Report them to you
   - You fix the code; I update docs/tests
   - Repeat until satisfied
   
5. **Commit & Push** — Once code review is clear:
   - Commit changes to the task-specific branch (naming: `task/description`)
   - Push to GitHub
   
6. **Create PR** — Open a pull request on GitHub
   - Include summary of changes and code review notes
   - Await your feedback
   
7. **Review Cycle** — When you provide feedback:
   - You edit code in `src/`
   - I update docs and tests as needed
   - You merge PR when satisfied
   
8. **Sync Main** — After PR is merged:
   - I pull latest main branch
   - Prepare for next phase

## Communication
- Keep responses concise and direct
- Reference files by path when specific locations matter
- When providing code guidance, be explicit about what to add/remove/modify
